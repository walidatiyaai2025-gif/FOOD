# FOODEX Built-In Job Role Catalog — Authoritative Matrix

Status: canonical governance reference for issue #2097  
Runtime authority: `backend/config/job_roles.php` + `backend/config/permissions.php` (legacy #96 mappings)  
Localization authority: `backend/lang/{ar,en}/job_roles.php`  
Reconciliation authority: `App\\Services\\BuiltInJobRoleCatalog::reconcile()`

## Governance rules

The table below is the reviewable onboarding matrix. Role codes are immutable. Built-in bundles are reconciled idempotently and are read-only in the normal Role Management UI; advanced custom roles remain supported by cloning/creating a custom role. A role with required enterprise modules is assignable only when those modules are operational. Store-scoped module roles additionally require the canonical store entitlement. Existing unavailable assignments are retained for audit/re-enable but contribute no effective permission while the required module/scope is unavailable.

Existing #96 roles (for example SUPER_ADMIN, B2B_ADMIN, B2C_STORE_ADMIN, OPERATIONS, INVENTORY, FINANCE, CUSTOMER_SUPPORT, RETAIL_* and Driver/Van roles) are mapped into this catalog without duplicate semantic replacement. Their permission default remains the established `config/permissions.php` matrix; new catalog roles use `config/job_roles.php`.

## Lifecycle semantics

- **Enable module:** predefined roles become assignable automatically; no existing user receives a role automatically.
- **Disable/suspend/unentitle module:** new assignment is rejected server-side. Historical assignments are retained, but `User::hasPermission()` and `effectivePermissionCodes()` ignore permissions contributed by that unavailable built-in role.
- **Re-enable module:** retained assignments can contribute permissions again only when the role's required lifecycle and scope entitlement are valid.
- **Upgrade role matrix:** change the canonical matrix and run the reference seeder/reconciler. Built-in roles converge deterministically; custom roles are never silently modified.
- **Authorization:** module entitlement is additive to RBAC and existing tenant/store/channel checks. SUPER_ADMIN protection and B2B/Retail isolation remain server-authoritative.

## User onboarding / role-management UX

The canonical Security & Users workspace remains `admin.security.index`. Normal onboarding/editing selects one or more localized business roles first. The role picker hides unavailable unassigned module roles, preserves and labels retained unavailable assignments, and shows localized domain/level/description context. Before save, it renders the selected role set and a deduplicated, business-readable combined effective-access preview. Raw permission editing remains an advanced custom-role workflow; canonical built-in matrices are protected from manual drift.

### Separation-of-duties advisories

Role assignment does not create a parallel authorization engine. High-risk combinations can be declared in `job_roles.risk_pairs` and are shown as localized, non-blocking warnings in the assignment UI. The initial canonical advisory is `PROCUREMENT_BUYER + PROCUREMENT_APPROVER`, reflecting procurement maker/checker separation. This warning does not weaken or replace server-side maker/checker controls: protected procurement/finance/treasury services remain authoritative for preventing the same actor from preparing and approving a protected transaction where policy applies.

## Customer Service order-action boundary

Customer Service staff deliberately receive `orders.manage`, `orders.dispatch`, and `finance.view` so the canonical Order Operations ellipsis can expose status decisions, execution assignment, payment state, and invoice view/print actions. This does **not** grant `orders.edit` or `finance.manage`: Customer Service cannot change commercial order lines/prices or post/settle/reissue Finance records. Team-owner reassignment remains separately controlled by `customer_service.team.manage`.

## Verification

Feature coverage lives in `backend/tests/Feature/BuiltInJobRoleCatalogTest.php` and protects deterministic reconciliation, module enable/disable, assignment blocking, stale-permission denial, store entitlements, two-role and three-role permission union/deduplication, mixed scopes, localized SoD conflict warnings, localization, and no-auto-grant behavior. Existing RBAC/navigation tests remain authoritative for channel/store privilege boundaries.
