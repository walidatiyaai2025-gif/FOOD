# FOODEX V2 P079 — Create/edit user by role-derived account channel and store

Issue #2815. Source: unified RBAC/ERP/sidebar discussion P079. Parent #2503. Foodex_V2 ONLY.

## Reuse → Extend, no parallel identity or authorization
Canonical Administration > Security > Users retains `SecurityController::storeUser`, `RbacManager::replaceUserRoles`, global role selection, retail-store role selection and audit logs. This PR adds a user-friendly explicit Account Scope/Channel selector (Global/Wholesale, Retail Store, Both), matching effective **requested** role assignment shapes. The new `account_scope` request is **optional for existing API/test clients** but required by the Dashboard UI. It is validated against authoritative submitted role assignments; never stored as a standalone permission, channel or customer type. A mismatch fails validation before creating anything. The real global role and store assignment are still checked by RbacManager for scope, actor grantability, active store, module entitlements and cross-tenant permissions.

Adds an auditable PATCH of management **identity only** (name, username, email, locale). Credential, role, store assignment, status and permission changes are intentionally excluded; channel/store editing continues through the existing audited role editor and its required business reason. Profile editing is limited to SUPER_ADMIN actors; Platform Owner, other SUPER_ADMIN identities, and platform customer accounts are excluded and fail HTTP 403. An email login change revokes API tokens and admin sessions, rotates remember token, and clears prior address verification. Every change records before/after and mandatory business reason; secrets never enter the audit. No mutation of financial, dispatch or order records.

## UI / language / field classes
Name and optional username are bounded legitimate free text; email is a validated unique login identity; locale and Account Scope are enums with AR/EN labels; global role and store role are authorized server-fed lookups; store is a real store lookup, never raw ID form. The user row derives current global/store/mixed, unassigned or platform-customer status from actual role assignments/identity flag. Forms retain desktop responsive/RTL/LTR and focusable native inputs/labels and keyboard-operable details. No new public API, separate Sidebar role policy, new client token or route for password changes.

## Tests and app impacts
Focused Laravel feature tests exercise global vs retail creation, strict scope mismatches with no write, backward compatibility of requests without account_scope, authorized profile changes with audit and session/token invalidation, protected identity and delegated actor HTTP denies, reason-required errors, AR/EN RTL/LTR UI. Existing full Laravel and real MySQL/Redis fresh install+upgrade+recovery CI must pass on exact final SHA before merge/close. Customer App no changed public customer routes, identity endpoints or Flutter; Driver App no Driver auth/assignment/GPS/wallet or Flutter; Van App no VAN auth/route/stock or Flutter. The changed route is management-only; all app login tokens for edited identity are intentionally revoked on email change, preserving existing security invariant. B2B VAN-only and B2C DRIVER-only unchanged.

No release/tag/main or production deployment. Manual UAT deferred to V2 final by #2503; do not claim browser/device acceptance. One Issue, one branch, one PR.
