# G008 / #3342 — V2 exact-source, three-application Android CI provenance

**Parent:** #2749 (G008), #2503. **Source:** FOODEX unified RBAC/ERP/Sidebar 2026-11-09 DOCX G008 / P112 / T115R04. **Branch:** Foodex_V2 only. **Release:** NONE.

## Defect and implemented slice

Existing per-app CI builds can be skipped independently based on changed paths. That is appropriate for ordinary PR speed, but it cannot prove that Customer, Driver and Van **all** have an Android artifact from the same final V2 candidate. The existing scripts/package-mobile-artifact.py provides one app's SHA-256 and source metadata but no independent three-app cross-check.

This new additive isolated CI workflow:

1. Runs on pull_request to Foodex_V2 for mobile code/build/provenance file changes. It explicitly checks out github.event.pull_request.head.sha rather than the synthetic PR merge commit. No trigger for main, Release publication, a default-branch-only dispatch, or deployment.
2. Runs negative Python provenance unit tests. Independently builds Customer, Driver and Van release-mode **CI validation** APKs in parallel from that head, using the existing approved Flutter generator and runtime endpoint/identity checks. The API origin is only a compiled constant in this validation, **not a request, runtime install or deployment**.
3. Packages each app once through existing package-mobile-artifact.py with exact PR source SHA, CI build number, APK file, SHA-256, length and native identity.
4. Downloads the three ephemeral GitHub Actions artifacts and runs scripts/v2-mobile-trio-provenance.py. The aggregator refuses missing/extra apps, split source SHAs, split app version/build, fake app identity, checksum/bytes mismatch, malformed or traversal filenames, symlink files/folders, false production readiness or a falsely trusted signing claim. A separate machine-readable v2-trio-provenance.json is uploaded for review.

## Signing and acceptance boundary

All three CI-only packages are generated by the Flutter template release APK workflow **with the template debug signing key** as recorded in manifest.json (signing=flutter-template-debug-key). They must **never** be represented as trusted staging-signed or production-ready artifacts. production_ready=false, trusted_signing=false, and release_published=false are preserved in the aggregate proof. There is no repository signing secret, Android store distribution, GitHub Release upload, Release directory modification or version promotion in this work.

If trusted staging signing is later introduced, it requires its own independent certificate/trust-root verification, explicit delivery approval, and a revised signed-artifact validator rather than renaming the debug signing mode. G008 cannot close on these CI-only APKs.

**No new mobile runtime contract:** Customer B2B/B2C API/auth/checkout remains unchanged; Driver remains B2C-only; Van remains B2B-only. No Flutter source, localization, notification, routing, dispatch or database code is changed. RTL/LTR, AR/EN, accessibility and operator UI untouched; separately scheduled mobile E2E and app acceptance gates are still required.

### Known limits

pull_request.paths is an intentional scope filter for the dedicated cost-intensive three-app certification. It is **not** an automatic certification of every unrelated backend-only PR. Because a V2 final source SHA changes after any merge, final G008 acceptance must rebuild/revalidate from the frozen exact isolated V2 source (with trusted staging keys) at final convergence. Ordinary per-app jobs and Required CI remain independent policy checks. This workflow cannot enforce branch-protection settings by itself.

No main, production, tags, store release, shared-host install or cPanel operations are authorized or executed.
