# V2 P091 — Scoped ALLOW and tenant/channel ceiling

**Issue:** #2828; **parent:** #2503; **source:** `FOODEX-Unified-RBAC-ERP-Sidebar-Discussion-2026-11-09.docx`, P091. **Integration only:** `Foodex_V2`.

## Existing surface, decisions and access contract

- **Domain:** Security / Retail operational RBAC. **Entity:** User permission override (per user/per store); Retail store assignment.
- **Actor:** Platform Super Admin may review/submit authorized overrides via the existing Security Center; Retail operational user receives *only* the selected per-store capability when the role/scope and permission domain are valid.
- **Placement:** Reuse the existing Dashboard Security Center user-permissions editor. No new screen, route, Sidebar entry or front-end primitive. Direct consumer: existing B2C orders workspace `/admin/b2c/orders?store_id=...` (and protected backend tenant-scoping consumers).
- **Authorization:** `RbacManager::replaceUserPermissions` validates Super Admin/managed permission and store assignment, persists difference from the target role baseline and records `user.permissions_changed` audit. `User::hasPermission` and `effectivePermissionCodes` enforce deny-over-allow, valid active role/store/channel and permission-domain constraints. `OperationalTenantScope::allowedStoreIds` now includes a **real authorized store-specific ALLOW** where an active B2C store-role assignment exists, instead of counting only inherited `permission_role` rows. Persisted scope key must exactly equal `store:<id>`; a spoofed store, stale assignment, mismatch, global/store DENY or B2B-only permission never becomes a B2C tenant candidate.
- **Security:** No new user-facing role grants, no blanket Super Admin bypass of tenant or SoD checks, no cross-tenant/channel movement. Matching active assignments are required. Only one additional bounded SQL query per scoped lookup with override flag, **not** one query per store; no new tables/migrations. The scope read path remains fail-closed on unknown channels.
- **Test:** `backend/tests/Feature/V2ScopedAllowTenantBoundaryTest.php` covers real Super Admin HTTP override write, persistent audit, AR/EN + RTL/LTR authorized B2C orders GET, cross-store 404, wholesale direct 403, shared role template immutability, forged foreign/B2B Store ALLOW rejection, global DENY precedence and revoked assignment. Related V2AllowScopeReadinessRegressionTest and V2DenyPrecedenceAuthorizationTest remain authoritative.
- **Operational failure/recovery:** Scope resolution is read-only and safe for retries; rollback of this code change does not alter persisted security grants. Before deploying any future release, audit stored overrides because reverting would re-hide legitimate ALLOW candidates. Never auto-insert/delete live user grants as part of migration.
- **AR/EN:** No new user-visible copy. Existing Dashboard templates provide locale and direction; the test verifies both. Responsive/focus behavior uses unchanged shared Security Center and Orders screens, so independent isolated-staging keyboard/viewport validation remains an acceptance condition.
- **Customer Flutter:** No application-specific changes; Customer identity/ordering API routes do not use the *admin store-role override* to grant customer permissions. Public request schemas, pricing/checkout, customer scope and DTOs unchanged. A Customer cannot acquire an active dashboard Retail store-role assignment through this change.
- **Driver Flutter:** No application-specific changes; a B2C driver's global driver role is not a Retail store-role assignment and this change cannot expand dispatch/delivery/gps access. Driver-specific guards and API surface unchanged; existing dispatch authorization tests in required CI remain mandatory.
- **Van Flutter:** No application-specific changes; B2B VAN ONLY fulfillment, vans/visit/routing guardrails and API schemas are not modified. The new candidate filter is B2C-store-only, preventing B2B Van entitlements from being inferred.
- **Dependencies/entitlements:** No feature/module enablement or readiness check is bypassed. Authorization continues through existing route/controller and module guards after `allowedStoreIds`. Finance maker/checker constraints untouched.
