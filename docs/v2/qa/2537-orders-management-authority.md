# V2 P207 — Authorized Orders Management navigation and HTTP acceptance

- Issue: [#2537](https://github.com/walidatiyaai2025-gif/FOOD/issues/2537); source Native DOCX P207; parent #2503.
- Target branch: `Foodex_V2` exclusively. Not a release, production change, live data verification or manual UAT approval.
- Delivery choice: **Reuse**, not a new page. Operations → Orders uses the existing `order_operations` Sidebar key and canonical `GET /admin/operations/orders` route (`admin.operations.orders.index`), rendered by `OrderOperationsController::index` and `admin.order-operations`. The `/admin/b2b/orders` and `/admin/b2c/orders` legacy routes already call the same controller with a fixed channel. No duplicate Orders ledger or UI.
- Domain/entity/role/goal: Orders & Fulfillment / order / authorized B2B operations or assigned B2C store operator / locate, filter and manage scoped orders. Workflow: existing filterable 25-row operations grid; placement: current Operations Sidebar child, no extra navigation entry; screen pattern: existing responsive operations workbench, Arabic RTL and English LTR.
- Permission and scope authority: canonical `orders.view` through `OperationalTenantScope::allowedStoreIds`; B2B filtered to `WholesalePrincipal::storeId()`, B2C to the user's allowed active Retail store IDs. Controller rejects `channel=all` with 403, unauthorized channel with 403, and a selected store outside the permitted scope with 404. Form validation and existing route guards remain unchanged; Sidebar display preferences cannot authorize a denied URL.
- Negative states: roleless and inactive users have neither menu entry nor direct HTTP access; cross-channel and cross-store requests fail at server; a saved cosmetic hide cannot disable the already authorized HTTP route or make another channel accessible.
- Module/readiness: `order_operations` is a canonical operational Orders route, **not** an ERP module-readiness proxy. No imaginary ERP/entitlement flag or decorative disabled-module bypass is introduced. The existing orders permission and tenant/channel authorization remain decisive. New ERP modules are separately gated by their own readiness controls.
- AR/EN/a11y: existing shared Dashboard shell renders `lang` and `dir` for both locales; this PR changes no templates, interactions, DOM landmarks or responsive styles. Focused regression verifies both localized screen responses.
- Automated evidence: `backend/tests/Feature/V2OrdersManagementSidebarAuthorityTest.php` covers wholesale and Retail Sidebar route parity, allowed rendered canonical page, roleless/inactive deny, cross-channel deny, cross-store deny, cosmetic hide separation, AR/EN direction. Existing `UnifiedOrderOperationsTest` remains authoritative for orders data, legacy route aliases, filters, order actions, and B2B/B2C operation lifecycle.
- Customer Flutter app: no API route, payload, storefront, login, or Customer order lifecycle change; this is an Admin Dashboard test-only verification.
- Driver Flutter app: no dispatch, assignment, GPS, wallet or Driver API change; Driver remains B2C only.
- Van Flutter app: no Van dispatch, visits, consignment, settlement or Van API change; Van remains B2B only.
- Safety: no schema changes, production user/order mutation, migrations, release artifact or deployment. Test data is synthetic and rolled back by `RefreshDatabase`.
- Acceptance: only claim complete when the issue PR's final exact-head Repository Policy, V2 Isolation and Required CI child jobs pass, and the PR merges into `Foodex_V2`. Manual browser/device/UAT is `DEFERRED_TO_V2_FINAL` under parent #2503, not falsely certified.
